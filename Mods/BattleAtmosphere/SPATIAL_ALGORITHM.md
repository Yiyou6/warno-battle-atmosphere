2026-11-06。**阶段：自定义分配器、通用自动入口和实时执行链已接通，当前安装 `spatial-runtime-preview.3`。preview.2 已由用户确认仍然扎堆；最新逐单位向前、正面/双翼分工与续进见 [方向展开](DIRECTIONAL_FRONTAGE.md)。完整前线算法与战斗分散验收未完成，没有发布“扎堆已解决”的 test4。** 以下保留整体算法设计，不代表所有阶段均已落地。

最新运行版本从真实玩家列表识别 AI，从当前部署区和导航网格生成局部候选位置，两个同阵营 AI 共用阵位预约，并以临时接管避免命令覆盖。测试里的 12 辆 AI 车辆均产生超过 25 m 的位移；实际间距尚不能保证持续达到目标。最新证据见 [原生接入记录](NATIVE_RUNTIME_RESEARCH.md)，已安装实现与边界见 [运行组件](Runtime/README.md)。下文区分完整设计和当前局部纠偏，早期研究记录保留为历史。

用户第三次反馈扎堆，否定了 test3 的实际分散效果。保留核心目标：最高难度遭遇战，沿前线较均匀、有作用地展开，少数主攻区适度集中；持续投入、有配合、有代价地争夺，不能出现大批无事可做的后方部队。

## 通用遭遇战要求

用户进一步明确：只要开启遭遇战，脚本就应自动工作。最终交付须满足：

- 共用遭遇战入口自动启动，覆盖任意地图的征服与歼灭；不要求逐地图安装或编辑场景。
- 地图边界、可通行区域、争夺目标、交战位置和单位状态来自当前对局。不得固化黑森林坐标、区域名、GUID 或专用标记。
- 阵营账本按当前对局的玩家及 AI 归属建立，不固定为四个 AI；友军玩家单位只计占位，不接受脚本命令。
- 前线方向、区段数量、阵位容量随地图与局势变化。没有实时数据时必须明确失败，不能回退到虚构坐标或另一张地图的缓存。
- 结束或重开遭遇战时释放上一局预约、单位 ID 和地图数据；不能将旧战场状态带入新局。

黑森林 4v4 征服保留为扎堆回归场景。通用性另需在不同尺寸、地形、人数和两种规则下验证，包含连续切换地图的生命周期检查。当前没有宣称这些实战检查已通过。

## 为什么这次需要更换方法

前几版修改的是任务数量、编组、通道约束和原生开关。它们没有建立“这个阵位已经分给谁、还有多少容量”的全阵营账本，也没有给我们直接控制每个目的地的能力。源码可证明此前没有自定义空间分配器；用户实测可证明此前配置没达到目标。截图本身不能证明到底是原生选点、行进路径、交战停步，还是多个 AI 目标重合造成的，不能把猜测写成已确认根因。

新算法必须同时控制最终阵位和行进过程。仅把最终坐标画得均匀，仍可能在桥口、道路出口或接敌点重新挤成一团。

## 整体设计与实现边界

| 层次 | 决策 | 本轮状态 |
|---|---|---|
| 战场观测 | 每个阵营维护稳定实体 ID、所有己方 AI 单位、玩家友军占位、有效任务与在途目标；敌情只能用该阵营已知情报 | 实时 ID、归属、坐标、兵种和部分活动状态已接入；不使用隐藏敌情作决策；完整任务语义待核验 |
| 前线提取 | 从有效交战/争夺区域得到可行动的前线曲线，按近似等宽区段采样；排除水面、不可达处、无射界无任务的后方 | 设计，真实地图实现待完成 |
| 阵位生成 | 结合地形、掩护、武器作用范围与兵种生成阵位，保持最小间隔；主攻通过更宽展开和有火力作用的纵深增加容量 | 已有当前导航网格、原生通行点检查、局部格点和横向区段；未实现掩护、射界与兵种纵深 |
| 全阵营分配 | 多个己方 AI 共用容量账本，把可用单位匹配到独占阵位；在途部队同样占名额；玩家友军只计占位 | 最小费用最大流已在游戏内求解；同阵营共用预约；按局部小批次纠偏，不等待全团 |
| 行进调度 | 选侧向入口与中间展开点；瓶颈路段采用有限时间窗预约，不允许多个队列同时挤入同一出口 | 设计，尚未实现；不能由终点间隔推导已完成 |
| 局部执行 | 避让近邻、炮击危险、堵塞和敌火；保持攻击/掩护任务，防止每次更新都打断射击；与原生 AI 明确命令归属 | 动态下令、临时接管、到位归还已接通；跳过识别出的活动单位；炮击/敌火避让未实现 |
| 反馈重规划 | 伤亡释放名额、增援补缺；有效任务短期保留；前线失效、严重拥挤或危险时立即解除保留 | 实时位置反馈、ID 失效/转属、停滞、期限、异常和退出归还已实现；完整前线补缺仍待完成 |

### 已实现的分配算法

实现：[allocator.py](Development/dispersion/allocator.py)。使用带容量约束的最小费用最大流，不是随机散开或每个单位各自选最近的点。

网络：`源 → 单位 → 阵位 → 前线区段 → 汇`。

- 每个单位最多分配一次，每个阵位容量为 1，区段总人数不得超限；所有候选阵位必须先满足间隔要求。
- 单位只能连向兵种适用且有可通行、战术可接受路径的阵位。没有边表示不可去，绝不自动补一条直线路径。
- 首先尽可能给全部单位找到有效任务；其次最小化各区段的凸拥挤代价；最后比较路径、风险及换任务代价。使用严格的整数权重顺序，距离便利不能压过可行范围内的前线覆盖。
- 区段第 `k` 个名额的边际拥挤代价为 `round(1000 × (2k+1) / w)`。相当于惩罚区段负载平方，越挤越难继续补兵。普通区段 `w=1`，少数主攻区段最多 `1.5`；主攻区数量最多约四分之一，只有少量区段时允许一个。
- 当前核心的区段应近似等宽，容量必须来自真实可用阵位。不同宽度、地形和交战价值的归一化由前线层完成，不能直接把任意地图通道当成等价区段。
- 同阵营四个 AI 统一计算一次，不能四份算法各自认为同一处还有空位。对立阵营单独计算，不共享隐藏敌情。
- 已下令但还没到达的单位保留阵位，避免下一轮再次把增援分到同一位置。死亡单位必须从权威快照移除，其预约随之释放。
- 仍然有效的短期任务可暂时保留，减少往返抖动。阵位/路径失效、紧急情况或单位已经挤在一起时解除保留。期限使用仿真时间，不用电脑墙钟时间。
- 玩家控制的友军不接收命令，但占用物理空间和所属区段容量。玩家自己把区段塞满时应报告不可满足约束，不能悄悄接管玩家部队。

运行组件按原生配置的每米 215 坐标单位换算，`120 m` 仍是待实战校准的目标间隔，不是炮击绝对安全距离。当前格点与到位容差不保证单位实际间距始终达到该值；主攻权重仍属完整前线设计，局部控制器当前使用相等区段权重。

### 不能通过后方囤积解决容量不足

当前线阵位不足时，要依次尝试拓宽可用侧翼、增加仍能实际支援交战的纵深位置、增援其他有效争夺目标、以单位替换而非持续叠加实现轮换。不能把无射界、无火力作用的后方坐标算作阵位。

若地形和兵力确实使“全部投入、有限密度、当前有效战斗范围”无法同时满足，算法必须报告不可行，并重新规划作战范围。当前核心将未分配单位列入 `unresolved`，`complete=false`，不生成“后方待命”命令，也不把部分成功冒充全体完成。**扩展作战范围与有时限的冲突处理尚未实现，所以当前原型还不能保证真实游戏无闲置。**

## 与原目标的耦合

| 关联目标 | 必须保留的行为与处理 |
|---|---|
| 持续投入、高代价争夺 | 分散后仍要有战斗任务和前推目标；不能靠减少购买、拖延出兵或无限等待腾位置来降低密度 |
| 步兵师对抗装甲 | 阵位按反坦克射界、掩护与支援关系分层；缺少坦克不等待组齐；核心支持角色可用性，但完整合成兵种配额尚未实现 |
| 坦克与步兵配合 | 装甲不因纯距离最优绕到无掩护的敌侧；危险和不适用路径应先排除；各单位间隔不等于让其逐辆无支援送死 |
| 炮火掩护 | 炮兵选点与前推区段关联；先压制再推进的时间协调属于执行层，当前分配器本身不指挥炮兵 |
| 防空与侦察 | 防空阵位覆盖当前分配的前沿，侦察提供区段情报；不能所有支援都跟到主攻中心 |
| 载员和运输车 | 运输途中按有效载员关系处理，不能给未下车步兵虚构已展开位置；有武装车辆卸载后可进入战斗分配；无武装载具不填前线作战名额 |
| 飞机与直升机 | 使用独立任务与航线层，不把地面阵位算法套到飞机上；此前空中支援设置保留，不宣称该算法解决盘旋问题 |
| 伤亡、撤退和补给 | 伤亡及时释放预约；真实撤退与补给保留必要控制权，结束后重新参加分配；不能强行取消恢复来凑“全员前线” |

## 早期游戏接入调查（历史状态）

已做只读程序和数据检查；没有修改 WARNO.exe、原版 DAT，没有操控界面。

1. 官方 `ndf_reference_manual.pdf` 第 3、6 页说明 NDF 用于描述对象，类型由引擎内部定义。新建模板并不会创建新的运行时算法类型。
2. `ExternalApi.dll` 导出的是认证、好友、云存档、工坊、平台等集成接口，导入 Steam API，没有核实到单位调度接口。
3. 原版 `DataCommon.dat` 含场景 `Scripting` 路径加载；原版及补丁 `ZZ_5.dat` 含 `XYZ0` 包装的 Python 2.5 字节码。已只读解析 11 个包的目录及 6 个相关模块，没有执行游戏字节码。
4. 找到了 `effetmapmultiplayer`、`leveldesign/launcher`、单位筛选、`TGDDescriptorMoveUnitGroup`、`TGDDescriptorGiveOrderStandard` 等内部脚本结构。打包的旧 `launcher.launch` 引用 `TEffetMapLauncher.RunScript`，但当前程序的 Python 绑定没有验证到这个接口，不能将旧制作工具字节码视为当前可调用的运行时接口。
5. 隔离 `-rootdata . -uselocaldata` 路径下，覆写共用 `ClusterLoadGameplay` 的遭遇战入口，已验证原生程序调用自定义模块的 `launch()`。目前只通过受控诊断异常取得证据；空包装对象的正常生命周期测试超时，不能称为对局成功加载。
6. 尚未验证：正常对局的完整生命周期、持续读取实体坐标/导航信息、接管下令而不被原生宏覆盖、存取状态及保持仿真确定性。固定场景动作图是候选研究方向，不能冒充已实现通用动态调度。

可复现脚本：[audit_runtime_hooks.py](Development/audit_runtime_hooks.py)；原始证据摘要：[runtime-hook-audit.json](Development/runtime-hook-audit.json)。数据目录格式参照作者源码 [moddingSuite EdataManager](https://github.com/kilivan4iK/moddingSuite/blob/master/moddingSuite/BL/EdataManager.cs)。另核查了 [WarnoModEditor](https://github.com/Jonitr0/WarnoModEditor) 和 [官方服务器说明](https://hub.docker.com/r/eugensystems/warno)：编辑器脚本和房间管理接口不能直接视为对局内单位算法入口。

当时的离线原型 `require_game_adapter()` 明确抛出未实现异常，该占位接口现在仍不冒充适配器。实际游戏入口已另行实现于 `Runtime/Python/ba_autorun.py`、`ba_space.py` 和 `Development/native_bridge`；最新证据覆盖上述早期接入缺口，但不覆盖完整前线行为。

## 验证与下一道交付门槛

运行 `Development/dispersion/test_allocator.py`。18 项测试覆盖扎堆输入分配、局部主攻、同阵营四 AI、容量耗尽、在途预约、伤亡补缺、不可达、兵种适用性、玩家占位、抗抖动和输入顺序确定性；另用 35 个小规模随机问题的穷举最优解校验求解器。

规模检查记录在 [validation.json](Development/dispersion/validation.json)：人工构造的 4 个 AI 共 240 个单位、6 个等宽区段，分配为每段 40 个；234 个单位包含一个主攻区时，分配为 54/36/36/36/36/36。两者目标阵位最小间距为 150 m、未分配数为 0；输入地形为人工可行场地，**没有模拟移动和战斗**。当前 Python 完整求解约耗时 3.77 s、3.04 s，不能直接当成逐帧实时算法；真实接入还需增量重规划、任务预算限制及必要的原生实现，并测量主线程开销。

这些测试验证的是目标分配，不模拟 WARNO 地形、行进、射击、伤亡或原生 AI 指令覆盖。真实交付必须依次证明：

1. 不改原版文件的模组加载路径能执行一个可观测的自定义入口。
2. 入口可持续获得真实己方状态，并对测试 AI 单位下达可撤销、可确认的命令；原生宏不会立即抢回控制。
3. 实现前线阵位生成、瓶颈通行和任务反馈，记录实际位置与下令回执；离线坐标图不算过关。
4. 不同地图、人数及征服/歼灭均能自动进入调度，切换对局后旧状态清空；不得依赖黑森林专用标记。
5. 黑森林 4v4 征服实测作为回归之一：连续覆盖、单位实际间距、局部炮击覆盖数量、在途拥挤时间和无效后方闲置一起验收，并回归首版的持续投入与高代价争夺。
